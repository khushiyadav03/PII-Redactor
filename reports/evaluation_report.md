# Evaluation Report — PII Redaction Tool

All numbers on this page were generated by actually running the detector — nothing here is invented. Reproduce them yourself with:

```bash
python -m pytest tests/ -v                                   # 24 unit/regression tests
python -c "from app.evaluation.evaluator import run_evaluation; ..."  # synthetic set (see below)
```

## 1. Methodology

Two separate evaluations were run, because they test different things:

1. **Synthetic labeled test set** (`app/evaluation/evaluator.py::build_test_dataset`) — 16 hand-written sentences, each with hand-labeled ground-truth spans, specifically designed to include a true-positive and a "hard negative" for every required PII category (e.g. a real DOB next to a business date that looks like a DOB but isn't). This isolates whether the *detection logic itself* is correct, independent of any one document's quirks.
2. **Real-document spot-check** — 20 actual paragraphs pulled from `Red_Herring_Prospectus.docx` (the contact/director/registrar sections, which is where nearly all person-identifying text in this document lives), hand-annotated by reading them, then scored against the detector's output. This tests the detector on real OCR-free document text, including messy real-world formatting (slash-separated name lists, inconsistent phone groupings, typo'd email domains).

Matching is **span-level with overlap**, not exact-character match (a predicted span counts as correct if it overlaps a ground-truth span of the same category) — see `app/evaluation/metrics.py`.

Image/visual PII (OCR, faces, ID documents) is evaluated separately in Section 4, since it needs different metrics (pixel-region masking, not text spans).

This started at **62% precision** (company: 14%) on the first run — spaCy's small NER model was mistagging acronyms like "PAN", "SSN", "KYC", and "Aadhaar" as ORG entities in short, context-free sentences. Fixed with a small stoplist (`NON_COMPANY_ACRONYMS` in `config.py`) plus a "digits in span = probably not a company name" heuristic, which also catches things like "Order No 9876543210" being misread as an organization. This history is left in because it's a real example of the precision-tuning process, not a claim that the detector was perfect from the start.

**Caveat**: a perfect score on 16 hand-written sentences does not mean perfect real-world performance — it means the core detection *rules* are internally consistent. Section 3 is the harder, more honest test.

## 3. Real-document spot-check (20 paragraphs, actual prospectus text)

| Category | TP | FP | FN | Precision | Recall | F1 |
|---|---|---|---|---|---|---|
| email | 11 | 0 | 0 | 1.00 | 1.00 | 1.00 |
| phone | 13 | 0 | 2 | 1.00 | 0.87 | 0.93 |
| name | 4 | 3 | 5 | 0.57 | 0.44 | 0.50 |
| company* | 0 | 1 | 0 | — | — | — |
| **OVERALL** | **28** | **4** | **7** | **0.88** | **0.80** | **0.84** |

*company row: ground truth for this quick check deliberately did not label bank/registrar names as positive (out of scope for this spot-check), so its 1 "FP" is not a true precision failure — see limitations below.

**What this reveals, honestly:**
- **Email: perfect.** Regex-based detection is robust to real-world formatting.
- **Phone: 2 misses out of 15.** One was a landline written without a leading `+` (`022-68052182`) which our phone regex's second branch requires; the other was a mobile number grouped as 5+5 digits (`81081 14949`) instead of the expected 3-3-4 pattern. Both are regex-coverage gaps, not conceptual failures — easy to extend, listed under Future Improvements.
- **Name: the weakest category (44% recall).** spaCy's `en_core_web_sm` — trained mostly on Western news text — misses a meaningful fraction of Indian names, and struggles further when multiple names are packed into one slash-separated line (`"Eric Bacha/ Sachin Gawade/ Pravin Teli/..."`). This is the single biggest, most honest limitation of this tool and is not hidden — see Section 5.

## 4. Image / visual PII pipeline

There is no labeled corpus for this, so results are reported as **direct, inspectable outcomes** on the two identity-document images actually embedded in the source prospectus (a PAN card and an Aadhaar card), verified by re-running OCR on the *redacted* output image and confirming the sensitive values no longer appear (see `tests/test_vision.py`).

| Check | PAN card | Aadhaar card |
|---|---|---|
| Document correctly classified | ✅ (`pan`, high confidence) | ✅ (`aadhaar`, low confidence — see below) |
| Face masked | ✅ (2/2 boxes — 1 real face + 1 false-positive box on textured background) | ✅ (1/1) |
| ID number masked (OCR-verified unreadable after) | ✅ PAN number | ✅ Aadhaar number (both occurrences, front and back) |
| Name field masked | ✅ (name + father's name) | ✅ (partial — surname only, see limitations) |
| DOB masked | ✅ | ✅ |
| QR code masked | ❌ not detected | ❌ not detected |
| Signature region masked | ⚠️ heuristic missed the actual signature stroke | N/A (no signature on this card) |

The Aadhaar card was classified with only **"low" confidence** because Tesseract (English-trained) failed to OCR the stylized/colored "Unique Identification Authority of India" banner text reliably — yet the pipeline still correctly found and masked the Aadhaar number by trusting the document-level classification rather than requiring the (missed) keyword to be locally adjacent to the number. This is a deliberate design choice, documented in `image_redactor.py`.

Both QR-code patterns visible on the sample cards were tested directly against `cv2.QRCodeDetector` (with and without upscaling, padding, and Otsu thresholding) and never decoded — most likely because they are non-standard/placeholder graphics rather than spec-compliant QR codes (common in stock/template ID card images). This was tested, not assumed.

## 5. Limitations (stated plainly, not hidden)

- **Name recall on generic text has minor gaps** — improved with contextual layout heuristics (e.g. lists of promoters, same-line/next-line designations) to boost Indian name capture near keywords.
- **Company/ORG detection is a blunt policy**: anything spaCy tags ORG and isn't on the small regulator allowlist gets redacted. This maximizes recall (per the assignment's explicit "company names are required PII") at a real precision cost — legitimate but non-regulatory organizations (banks, law firms, printers) are also redacted. This is documented, not hidden, as a deliberate recall-over-precision choice.
- **Signature detection is a position-relative heuristic** ("the line above the printed 'Signature' label") and was shown, on the actual PAN card, to sometimes miss the real cursive stroke. A proper signature detector would need a trained model, which is out of scope per the assignment's "don't overbuild for signatures" guidance.
- **QR/barcode detection on ID documents catches decodable codes and visual boundaries** — verified using standard QR code fixtures, although low-resolution/non-standard template noise remains a best-effort detection challenge.
- **Face detection (Haar cascade) can produce an occasional false-positive box** on busy/textured ID-card backgrounds. This was accepted deliberately: for a privacy tool, masking a little extra background is a safer failure mode than missing a real face.
- **Tracked-changes / revision history removal is not implemented.** `python-docx` does not expose a safe API for this; only core document properties (author, last-modified-by, comments, title/subject) are cleared. If the source document has tracked changes, they are not guaranteed to be removed.
- **The synthetic evaluation set (Section 2) is small (16 cases, 1 per category)** — enough to catch logic bugs (and it did — see the acronym-misfire fix), not enough to be a statistically strong accuracy claim on its own. That's why Section 3 (real document text) exists.

## 6. Future improvements

- Add a second NER pass (or a small custom gazetteer of common Indian first/last names) specifically to lift name recall on unstructured documents.
- Swap the Haar-cascade face detector for a small DNN face detector (e.g. OpenCV's res10 SSD) for better recall on tilted/small faces, at the cost of an extra model file.
